without re-deriving anything below. No lab YAML, `config/refplat.txt`,

`docs/superpowers/specs/2026-09-12-trustsec-phase1-routed-ise-design.md`

## Why this exists

The operator needs to show Cisco, and a customer, that ISE profiling
can approach what ForeScout currently does for agentless NAC and
inventory, ahead of migrating a real environment off ForeScout/Arista
onto ISE/Cisco. They have a real ForeScout output example and their
own five-step SNMP profiling procedure to approximate. A standalone
Nexus/SNMP profiling proof was considered and scrapped: profiling
belongs on the access layer, so it moved into the TrustSec lab instead
of standing alone.

## What's confirmed so far

**The Phase 1 C8000v cannot be the access-layer device.** Tested live
against the `edge` node in `labs/trustsec-phase1.yaml` rather than
assumed, on GigabitEthernet2:

| Command | Result |
|---|---|
| `switchport mode access` | Rejected: `% Invalid input detected` |
| `mab` | Accepted |
| `dot1x pae authenticator` | Accepted |
| `authentication port-control auto` (IBNS 1.0) | Accepted |
| `access-session port-control auto` (IBNS 2.0) | Triggered its own irreversible CPL-conversion prompt |

The router has no switchport concept at all, confirming the operator's
own instinct that a real Catalyst switch is needed for genuine
endpoint-facing MAB, 802.1X, and profiling. The C8000v's role stays what
Phase 1 already proved: RADIUS and CoA transport, not the access edge.

One live side effect to know about before the next session touches this
node: the IBNS 2.0 conversion prompt above resolved to its default
"yes" on its own, from a stray keystroke in the test script, before it
could be declined. GigabitEthernet2 currently carries a converted
`access-session` configuration plus an autogenerated
`service-policy type control subscriber POLICY_Gi2` in running-config.
The interface is still administratively down and nothing was saved to
startup-config, so a reload of that node reverts it; no action is
needed unless the node is reloaded and someone wants the old config
back, in which case just don't save first.

**Both Catalyst 9000v flavors are already downloaded, no new image
acquisition needed.** Mounted `software/refplat-20260409-fcs.iso`
read-only and confirmed `cat9000v-uadp` and `cat9000v-q200` are both on
it, node definitions and images. Read both node-definition YAMLs in
full:

- Both are real switches: 24 physical `GigabitEthernet1/0/1` through
  `/24` switchports plus a `GigabitEthernet0/0` management port, unlike
  the C8000v's routed-only interfaces.
- Both run `pyats: {os: iosxe, series: cat9k}` and point at the same
  Catalyst 9300 series CCO documentation page.
- The only differences in the definitions themselves: UADP asks for 18
  GB RAM, Q200 for 12 GB, both 4 vCPU, and a different internal
  `board_id` selecting which ASIC the simulation models. Both are
  labeled BETA with no Cisco support.

Working recommendation, not yet a decision: UADP, because that ASIC
family is what actually sits in the fixed-access, wiring-closet
switches (9200, 9300) that real TrustSec/ISE access-layer deployments
run on, and the pitch here is specifically about that access layer. Q200
is the lighter option, 12 GB against 18, if Azure VM capacity on the CML
host is tight. Neither variant's dot1x/MAB/TrustSec behavior has been
tested live yet; that has to happen once one is in the topology, the
same way the C8000v's limits were confirmed rather than assumed.

**The image pipeline doesn't need a special destroy.** Traced
`scripts/10-upload-images.sh`, `05-persist.sh`, and `cml.sh` in
`vendor/cloud-cml` rather than guessing:

- Uploading a new image to the persistent blob (`config/refplat.txt`
  plus `scripts/10-upload-images.sh`) is an `azcopy copy
  --overwrite=false` against Azure storage. It doesn't touch the CML VM
  and can happen whether or not one is currently running.
- A CML VM only learns about a node definition at its own boot-time
  provisioning: cloud-init reads the rendered refplat list and copies
  from blob into the VM's local image store. The persistent data disk
  already holds every image copied so far, so a rebuild that reuses it
  only fetches what's new.
- So the switch becomes usable the next time the disposable CML VM goes
  through its normal teardown and rebuild, which this environment
  already does every session (`docs/decisions/0002-three-terraform-roots-by-lifetime.md`).
  No extra or unplanned destroy is needed beyond that ordinary cycle,
  and that cycle still needs the operator's explicit go-ahead each time
  it runs, same as always.

## Update, 2026-09-17: images live, transit bridge built, RADIUS not yet answered

Where the build stopped when the session ended, in order of what a fresh
session needs to know.

**Done and on the controller.** Both `cat9000v-uadp` and `cat9000v-q200`
are in blob and registered on the running controller through the
dropfolder and `POST /images/upload` (LESSONS-LEARNED). A scratch lab
"cat9kv probe" (`f13f801f`, not tracked, YAML in the session scratchpad)
runs one UADP switch `sw1` at 10.100.0.3 on the transit bridge with an
alpine `ep1` on Gi1/0/1. The CLI probe on that switch accepted every
command that matters: `switchport mode access`, `mab`, `dot1x pae
authenticator`, `access-session port-control auto` (with the one-time
IBNS 2.0 conversion prompt), `cts role-based enforcement` globally, per
VLAN and per interface, `cts role-based sgt-map`, `cts manual` with
`policy static sgt` and `propagate sgt`, `cts sxp enable`,
`device-sensor`, `ip dhcp snooping`, `device-tracking policy`. Licensing
shows `network-advantage` and `dna-advantage`. `cat9kv-sw1` (10.100.0.3)
is a network device in ISE, created through `ise_config.py`.

**The routed path exists now, host side.** It never had: STATUS from
2026-09-13 recorded that `06-transit-bridge.sh` "never landed", and the
Phase 1 pyATS run had never executed. The fork now carries it as a
libvirt routed network named `transit` with bridge `bridge1` (the
controller's scan only accepts `bridgeN`, `virbrN`, `vlanN`, `localN`),
host 10.100.0.1/24, the /16 routed to the edge at 10.100.0.2, autostart.
It was run by hand on the live host, the connector "Bridge 1" is
registered, and both labs' connector nodes point at `bridge1` and are
`BOOTED` with taps on the bridge. The tracked `labs/trustsec-phase1.yaml`,
`scripts/90-smoke-test.sh`, and `verify/trustsec-phase1/verify.py` use
`bridge1` now. PR #11 carries all of it.

**What works on the wire, proven with tcpdump on the host.** The switch's
RADIUS Access-Request arrives on `bridge1`, the host forwards it out
`eth0` toward 10.20.2.20 (firewalld no longer rejects; the `!A` of the
netplan version is gone). Azure Network Watcher confirms the ISE end:
ISE's effective route to 10.100.0.3 is the UDR via 10.20.1.10, its NSG
allows the request in (`allow-radius`) and the reply out.

**What does not work yet, and where to look.** No reply ever comes back:
nothing from 10.20.2.20 on `eth0 In` in a 40 second capture with a
request every few seconds. The one hop Azure's tooling could not test is
the CML NIC's outbound NSG evaluation of a forwarded packet whose source
(10.100.0.3) is not a VNet address; `test-ip-flow` refuses a local IP
that is not the NIC's own. The other possibility is ISE receiving the
request and not answering. Next step, in order:

1. Look from ISE's side. Either the RADIUS Live Logs in the GUI (the `ise`
   tunnel in `config/tunnels.conf` forwards local 8443), or `tech dumptcp 0
   count 12` on ISE's CLI, which is SSH key-only: the try with
   `keys/cml-lab` was interrupted before it ran, so first confirm which
   public key the Marketplace deploy was given. If ISE sees no request,
   the drop is on the Azure side between the CML NIC and ISE.
2. If it is the CML NIC, add an explicit outbound rule on its NSG for
   source 10.100.0.0/16 to the apps subnet, any port, rather than relying
   on the `VirtualNetwork` tag. That NSG is defined in the fork, not the
   persistent root: `azurerm_network_security_group.cml` in
   `vendor/cloud-cml/modules/deploy/azure/main.tf`, beside the existing
   `lab_transit` inbound rule, so it is a stop-and-ask vendor edit that
   lands on the next build.
3. If ISE sees the request and does not answer, check Operations >
   RADIUS > Live Logs for the drop reason (unknown NAD, shared secret).
   Both NAD entries read back correctly over ERS (RADIUS, /32, profile
   Cisco), so the secret is the first suspect after the NAD lookup.
4. Only then: MAB on `ep1`'s port, the first real session, and the
   Phase 2 spec (FTDv and Kali added to the topology, FTD enforcing by
   SGT with inline tagging on its inside interface, cdFMC managed).
